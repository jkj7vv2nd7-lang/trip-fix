# 設計報告書 ― 学習アプリ「TripFix」

作成：2026-11-15
位置づけ：清水さんが持参した仕様書と、メインで承認された方針（フェーズ0）を受けた設計。
改訂：2026-11-15、設計承認。アプリ名は「TripFix」に決定（躓き＝trip を直す＝fix、という意味合いで清水さんが候補から選択）。リポジトリ名は trip-fix を想定。§10 の確認点はすべて設計どおりで承認された。

## 0. 前提（承認済みの方針）

- 単体HTML（1ファイル）で作り、GitHub Pages で公開する。データは端末内のみ。答案の写真も端末の外に出ない。
- 写真の読み取りは2段構え。標準は「写真を記録として残し、問題ごとの情報はタップ中心の速い入力で確定」。任意AIモード（Bridge Note と同じ複数プロバイダ切替方式、既定オフ、利用者自身のキー）を使うと、写真からの下書き読み取りと解説の下書きができるが、**必ず本人の確認・修正を通してから保存**する。
- 補強プリントの問題は「型＋数値テンプレート」から生成し、答えはアプリ内で計算・検算する。検算を通らない問題は破棄して作り直す（答えの誤り0件を、作り方で保証する）。
- PDFは印刷方式（A4、解答は最終ページ、図形はSVG）。
- 共有リンクは作らない（サーバーがないため）。代替は項目を選べる「まとめ印刷・書き出し」。
- 数式は教科書表記（累乗は真の上付き、根号は中身全体に上線、分数は横棒、変数はセリフ体イタリック）。
- v1 は中学数学で「核の循環」まで。週間レポート・達成マップ・ミス復習ラジオ・口頭テスト・最終確認プリント・「同じミス」警告の間隔調整は v1.1 以降。高校範囲の単元・テンプレート拡充と小学校算数は最終段階。
- 解説の読み上げは Web Speech API。数式の読み替え規則を本設計に含める。
- 全画面に「この解説は正しくないかも」の報告ボタンの置き場を設計に含める。

### 既存アプリとの役割の違い

- 「算数・数学つまずき診断＆補助プリント」は**先生側**の道具（誤答パターンから原因を逆算し、専用プリントを作る）。本アプリは**生徒自身**のノート（自分の答案を写真で残し、自分のミスの循環を管理する）。設計思想（原因から考える、検算で正確さを担保する）は共通だが、データの持ち主と主画面が違う。
- AIモードの土台（プロバイダ切替・キー管理・接続テスト）は Bridge Note の実績ある形をそのまま踏襲する。

- どの画面からでもホームに戻れる。作業の途中状態（未確定の答案）は下書きとして残り、ホームに「つづきがあります」と出る。
- 生徒の利用を考え、1画面に詰め込まず、手順が分かる遷移にする（撮影→確認→分析、と段階を踏む）。
- 色だけに頼らない表示（○×・タグは形と文字でも区別）、大きなタップ領域、ダークモード対応を最初から入れる。

## 2. 端末内データ設計

仕様書のデータ案（Student／Exam／Question／Answer／ErrorAnalysis／Unit／Worksheet／GeneratedProblem／ReviewSchedule／WeeklyReport／ShareLink／CorrectionLog）を、単体HTML向けに次の形に翻案する。

### 2.1 保存場所の分担

- **文章データ**（答案の情報・分析・設定など）：localStorage に JSON で保存。キーは版管理つき（例：`missnote-v1`）。保存のたびに全体を書き直す単純な方式とし、壊れた場合に備えて直前のバックアップを別キーに1世代残す。
- **写真**：IndexedDB に Blob で保存（localStorage は容量が小さく写真に向かないため）。文章データ側には写真のIDだけを持つ。
- **AIのキー**：Bridge Note と同じく localStorage（端末内のみ、プロバイダごとに分けて保存）。

### 2.2 データ構造（主なもの）

- `profile`：ニックネーム（任意）、学年。志望校などは持たない（最小限）。
- `exam`（答案）：id、撮影日、テスト名（任意）、教科（v1は数学のみ）、写真IDの配列、状態（下書き／確定）。
- `item`（問題）：examId、問題番号、問題文（テキスト＋数式記法つき文字列）、配点、自分の答え、途中式（行の配列、任意）、○×△、得点、単元ID、原因タグ（複数可）、原因の根拠メモ、最初のミス行（任意）、先生の赤ペンコメント（任意・手入力またはAI下書きから）、正答（任意：手入力またはAI下書き。解説と検算の材料）。
- `analysis` は item に内包する（単体HTMLでは正規化しすぎない方が壊れにくい）。
- `worksheet`（プリント）：id、作成日、設定（問題数・対象）、生成問題の配列（型ID＋パラメータ＋問題文＋答え＋解き方。種を残すので再印刷が同じ内容になる）、解き直し結果（問題ごとの○×と日付）。
- `unitMaster`（単元マスタ）：アプリ内蔵の定数データ（§3）。利用者データではない。
- `correctionLog`（修正履歴）：AI下書きをどう直したかの記録（種類と件数のみ。答案の内容そのものは含めない）。将来の改善材料として端末内に蓄積。
- `reportLog`（報告）：「この解説は正しくないかも」の記録（対象の解説ID、種類、日時）。サーバーがないため送信はせず、設定画面で一覧でき、書き出しに含められる。
- `settings`：学年、読み上げ速度、文字サイズ、ダークモード、AI設定。
- ShareLink は作らない（§9の制限）。ReviewSchedule と WeeklyReport は v1.1 で追加する。

### 2.3 写真の保存方式と容量の考え方

- 取り込み時に長辺1600pxへ縮小し、JPEG（画質0.8）で保存する。答案1枚あたり約300〜500KBが目安。
- 容量の見積もり：答案30回分×3枚×約400KB ≒ 約36MB。1年使っても100MB前後に収まる想定。
- ただし iPhone（Safari）のブラウザ保存は上限と削除ポリシーが端末依存で、長期間使わないと消える可能性がある。対策として、(1) 設定画面に使用量メーター（写真の枚数と合計MB）を出す、(2) 一定量（例：150MB）を超えたら古い答案の写真を「圧縮して残す／写真だけ消して記録は残す」を選べる導線を用意する、(3) データの書き出し（バックアップ）をホームと設定からいつでもできるようにし、アプリ内でも定期的に勧める。
- マスキング：撮影・追加の画面で、写真の上に黒い四角を置いて名前・学校名などを塗ってから保存できる（保存前の元画像は残さない）。

## 3. 原因タグと単元マスタ

### 3.1 原因タグ（仕様書の10種をそのまま採用）

知識不足／公式の使い間違い／計算ミス／符号ミス／単位の書き忘れ／問題文の読み違い／解法が思い浮かばない／時間切れ／作図・図の読み取りミス／その他

- ×・△の問題に複数付けられる。タグごとに「根拠」の短文を残せる（例：「2行目で −3 を移項するとき符号が変わっていない」）。
- 原因タグは分析グラフとプリントの対象選択の軸になる。
- 途中式が行単位で入力されている場合のみ、「最初のミス行」を指定できる（写真だけから行単位の自動特定はしない。§9）。

### 3.2 単元マスタ（v1：中学数学の全範囲をタグ付け対象にする）

タグ付け・分析のための単元マスタは中学の全範囲を用意する（学習指導要領の構成に沿う）。

- 中1：正負の数／文字と式／一次方程式／比例・反比例／平面図形／空間図形／資料の分析
- 中2：式の計算／連立方程式／一次関数／図形の性質と証明／確率
- 中3：多項式（展開・因数分解）／平方根／二次方程式／二次関数（y=ax²）／三平方の定理／円の性質／標本調査

各単元には「前提単元」を持たせる（例：連立方程式 ← 一次方程式・文字と式）。解説の「やさしく」で前提に遡るときと、分析で「土台の単元から復習」の提案に使う。

### 3.3 テンプレートが用意できる範囲との区別

単元マスタ（タグ付け用）と、プリント生成テンプレート・内蔵解説パターンが対応する範囲は別物として扱い、画面でも正直に区別する。v1 の生成・解説パターンの対応範囲は §5 の約24型。範囲外の単元の問題は、記録・タグ付け・分析・（正答を入力すれば）原因別解説まではできるが、補強プリントの自動生成は対象外である旨を表示する。

## 4. 解説エンジン

### 4.1 解説の構造（全モード共通）

順序は仕様書どおり固定する。

1. 自分の解答のどこが違うか（自分の答えと正答の差分、最初のミス行があればそこを指す）
2. 正しい考え方（なぜその解き方になるか）
3. 正しい解き方（手順）
4. 同じ型の問題を見分けるコツ（問題文のどの言葉・形に注目するか）

深さは3段階：「やさしく」（前提単元まで遡る説明を足す）／「ふつう」／「くわしく」（別の見方や検算の仕方を足す）。切り替えは同じ材料の出し分けとし、内容の正しさは段階で変えない。

### 4.2 内蔵パターン（AIなしで動く範囲）

- 問題が生成テンプレートの「型」に結びついている場合（自分で作ったプリントの解き直しや、確認画面で型を選んだ場合）：型のソルバーが正答と手順を持っているので、①〜④を具体的に生成できる。自分の答えが数値・式として入力されていれば、差分の指摘（符号・係数・値のずれ）まで自動で出す。
- 型に結びつかない問題：原因タグ別の解説パターン（タグ×単元の文章の骨組み）に、正答（手入力またはAI下書きで確定したもの）を差し込んで出す。正答が無い問題では、①③は「正答を入力すると、ここに具体的な解説が出ます」と正直に表示し、②④（考え方とコツ）だけを出す。
- 内蔵パターンの文章はすべてアプリ側で用意したオリジナルの文面とし、数値は差し込み時にアプリが計算したものだけを使う（文章側に計算結果を持たせない）。

### 4.3 AIモード（任意・既定オフ）

- Bridge Note 方式：プロバイダ（Gemini／OpenAI／Claude／OpenAI互換／Ollama）を切り替え、キーとモデルはプロバイダごとに保存、接続テストつき。既定はオフで、オフのときは通信を一切しない。
- 用途は2つ。(a) 写真からの下書き読み取り：画像を送り、問題ごとの下書き（問題文・自分の答え・○×・配点・単元・タグの候補）を構造化形式で受け取り、確認・修正画面に「下書き」として流し込む。(b) 解説の下書き：①〜④の文章案を受け取る。
- どちらの下書きも**未確定の印つき**で表示し、本人が確定するまで保存データにならない。数値・答えを含む下書きは、型に結びつく問題ではアプリの検算と突き合わせ、不一致なら警告を出す。突き合わせできない問題の下書きには「AIの下書き（検算できていません）」と明示する。
- 写真を外部AIに送ることになるため、AIモードを初めて有効にするときは、その旨と「名前などが写っている写真はマスキングしてから」を平易な言葉で確認する。

### 4.4 報告ボタン

- 解説画面とプリントのプレビューに「この解説は正しくないかも」ボタンを常設する。押すと種類（答えが違う／説明が分かりにくい／その他）を選んで記録できる（reportLog、端末内のみ）。
- 全画面のフッターにも小さな入口を置く（仕様書の「全画面に設置」に応える形。実体はその画面の文脈に紐づく報告として記録）。

## 5. 問題生成テンプレートと検算

### 5.1 型の持ち方

型（テンプレート）は次の部品で構成する。

- `gen(rng)`：パラメータの範囲と条件（例：解が整数になる係数だけを引く）から問題を作る
- `solve(params)`：模範解答と解き方の手順を作る
- `verify(params, answer)`：**生成とは別の経路**で検算する（方程式なら解を代入して両辺一致、確率なら全事象の数え上げと比較、図形なら寸法の再計算）
- `statement`：問題文の組み立て（数式は教科書表記の部品で組む。図形は問題文と同じパラメータからSVGを描く＝図と文の不一致を起こさない）

採用条件：答えが一意／数値がきれい（分数は小さい分母まで、根号は簡約済みで中身が小さい）／難易度が型の想定内。満たさなければ破棄して引き直す（上限回数つき）。生成のたびに検算を通すため、出題される問題の答えの誤りは構造的に0件になる。

### 5.2 v1 で用意する型（見込み：約24型）

| 単元 | 型 |
|---|---|
| 正負の数 | 四則の混合計算／累乗と絶対値 |
| 文字と式 | 式の値／一次式の加減 |
| 一次方程式 | 基本形／分数・小数係数／文章題（数と金額） |
| 式の計算（中2） | 単項式の乗除 |
| 連立方程式 | 基本形／文章題（割合と速さ） |
| 展開・因数分解 | 式の展開／因数分解 |
| 平方根 | 根号の計算／分母の有理化 |
| 二次方程式 | 因数分解で解く／解の公式 |
| 比例・反比例 | 式を求める |
| 一次関数 | 2点から式を求める／グラフの読み取り（SVG） |
| 二次関数 | 値の変化と頂点 |
| 確率 | サイコロとくじ／場合の数（並べ方・組み合わせ） |
| 図形 | 角度の計算（SVG）／三平方の定理（SVG） |

- プリントの構成：類題（同じ型・新しい数値）→ ひねった問題（型の変化フラグ：符号の反転、分数係数、問いの向きを変える）→ 再挑戦（間違えた問題と同じ型の新規問題。**元の問題そのものは載せない**。権利への配慮として仕様書の原則を守る）。
- 解答と解き方は最終ページにまとめる。

## 6. 読み上げの数式読み替え規則

解説文は、表示用（教科書表記）と読み上げ用を分けて持つ。読み上げ用は次の規則で機械変換したうえで、内蔵パターンの文章は読み上げ用も手で用意する（変換だけに頼らない）。

| 記法 | 読み |
|---|---|
| x^2、x^3 | エックスの2乗／エックスの3乗 |
| x^n（一般の指数） | エックスのn乗 |
| √3 | ルート3 |
| √(x+1) | ルート かっこ x たす 1 かっこ閉じ（根号の範囲をかっこで明示） |
| a/b（単純な分数） | b 分の a |
| (a+b)/(c+d) のような分数 | かっこ c たす d かっこ閉じ 分の かっこ a たす b かっこ閉じ（分子・分母に演算がある場合はかっこ読み。分数は単純な場合と同じく分母から読む ― 実装時に表記を統一） |
| = 、≠ | イコール／等しくない |
| <、>、≦、≧ | より小さい／より大きい／以下／以上（数直線の文脈では「未満」を使い分ける） |
| ± | プラスマイナス |
| \|x\| | 絶対値 x |
| a_n（添字） | エーの n（添字はそのまま読む） |
| π | パイ |
| 30° | 30度 |
| 25% | 25パーセント |
| a：b（比） | a 対 b |
| (2, 3)（座標） | 座標 2、3 |
| sin、cos、tan | サイン／コサイン／タンジェント（高校範囲。v1では読み替え表にのみ用意） |
| △ABC | 三角形 ABC |
| ∠A | 角 A |
| AB⊥CD、AB//CD | AB は CD に垂直／AB は CD に平行 |

再生の作り：文単位に区切って読み上げ、再生中の文をハイライトする。速度は3段階＋スライダー、一時停止・再開・「もう一回」。iPhone では音声合成の開始にユーザー操作が必要なため、再生ボタン起点を徹底する。一文が長い場合は句読点でさらに割る。

## 7. 印刷レイアウト

### 7.1 補強プリント（A4）

- 1ページ目以降：表題（プリント名・名前欄・日付欄・目安時間）、問題（番号・配点の目安つき）、途中式を書く余白（問題ごとに罫線エリア）、図形はSVG。
- 最終ページ：解答と短い解き方（「解答ページ」と明示し、切り離せるよう改ページで独立させる）。
- 印刷時はプリント部分だけが紙に出る（画面のボタン類は印刷対象から完全に外す）。白黒でも読める線の太さと濃さにする。B5は v1.1 で追加（用紙設定の追加のみで済む形にしておく）。

### 7.2 まとめ印刷（共有リンクの代替）

- 選べる項目：答案ごとの失点内訳（原因別の横棒グラフ）／単元別の傾向／解き直しの記録（回数・克服数）／期間の指定。
- 初期状態では答案の写真と点数は含めない（仕様書の共有方針に合わせ、含めたい場合だけ本人が選ぶ）。

## 8. フェーズ計画と受け入れ確認の観点

### v1（核の循環）

- **フェーズ1：土台と記録** ― アプリの骨組み、撮影・追加（マスキング含む）、確認・修正、保存と再表示、ホームと一覧、設定の土台、容量メーター。
  受け入れ：架空の答案（一次関数・二次方程式・図形・確率の4種、中学範囲）で「追加→確認→確定→再表示」が通る。写真なしの手入力だけでも答案を最後まで作れる。写真の縮小と容量表示が正しい。
- **フェーズ2：分析と解説と読み上げ** ― 原因タグ、分析画面（答案ごと・全体）、内蔵解説（型に結びつく問題は具体版、それ以外は原因別＋正答差し込み）、3段階の深さ、読み上げ（読み替え規則・文単位ハイライト）。
  受け入れ：4種の答案で分析の集計が手計算と一致する。型に結びつく問題の解説の数値がすべて検算と一致する。読み上げで数式が規則どおり読まれる（主要パターンの実機確認含む）。
- **フェーズ3：プリントと解き直し** ― 生成エンジン（約24型）、プリント作成と印刷、解答ページ、解き直しの記録、まとめ印刷・書き出し。
  受け入れ：生成問題100問の自動検証で、答えの誤り0件（検算を通らない問題が出題されないことの確認を含む）。A4印刷で解答が最終ページに来る。図形問題の図と問題文の数値が一致する。解き直しの記録が分析に反映される。
- **フェーズ4：AIモードと仕上げ** ― プロバイダ切替、写真の下書き読み取り、解説の下書き、確認フローの徹底、報告ボタン、説明画面（データの扱い・AIが誤る可能性の明記）、全体の表示確認（幅360px・タブレット・PC）。
  受け入れ：AIオフでは通信が起きない。下書きは確定操作なしに保存されない。検算と合わない下書きに警告が出る。キーが端末の外に出ない（自分のプロバイダ以外に送られない）。

### v1.1 以降（段階追加）

- v1.1：ミスのクセ週間レポート（根拠の実例つき、対策は1〜3個まで）／達成マップ（単元ごとの色分け）／「同じミス」警告（間隔は克服状況で調整）／最終確認プリント（テスト範囲と残り日数で分量調整）／B5印刷。
- v1.2：ミス復習ラジオ（今日の×を約5分にまとめて連続読み上げ）／口頭テスト（音声認識は候補提示＋本人の確認を前提にする）。
- 最終段階：高校範囲（三角比・場合の数と確率の発展など）の単元マスタとテンプレートの拡充／小学校算数（分数計算など）の対応。受け入れ用の答案データ（小学校の分数計算）はこの段階で使う。

## 9. 既知の制限（正直に）

- **共有リンクは作れない**：サーバーがないため、期限つきURLの発行はできない。代替は「まとめ印刷・書き出し」（§7.2）。リンク共有がどうしても必要になった場合は、サーバーを足す別企画として切り分ける。
- **手書き答案の完全自動読み取りはできない**：標準モードでは写真は記録であり、内容の確定は本人の入力による。AIモードでも読み取りは下書き止まりで、誤読がありうるため確認・修正が必須工程になる。読み取りの自信度という考え方は、AI下書きの項目ごとの「要確認」印として取り入れる（数値化した自信度は、AIの自己申告を鵜呑みにしないため表示しない）。
- **途中式の自動解析はしない**：「最初のミス行」は、途中式を行単位で入力・確定した場合にだけ指定できる。写真だけから行単位の誤りを自動で特定することは v1 では行わない。
- **内蔵解説の具体度には差がある**：型に結びつく問題では自分の答えとの差分まで具体的に出せるが、自由な問題では原因別の考え方・コツが中心になる（正答を入力すれば差分の材料は増える）。AIモードの下書きも、検算で裏付けできないものはその旨を表示する。
- **音声認識は不安定**：iPhone のブラウザ音声認識はこれまでの自作アプリでも不安定なことが確認されている。口頭テストを v1.2 に置き、候補から選ぶ確認方式にするのはそのため。読み上げ（合成）側は比較的安定しているが、声質と数式の読みの自然さは端末に依存する。
- **写真とデータの保全は端末任せ**：ブラウザの保存領域は、端末の空き容量やブラウザの判断で消えることがある。書き出しによるバックアップをアプリ内で勧めるが、自動のクラウド保存はしない（写真を外に出さない方針と両立しないため）。
- **オフライン動作**：単体HTMLの単純さを優先し、サービスワーカーによる本格的なオフライン化は v1 ではしない。Pages から読み込んだ後は多くの場面で動くが、保証はしない。
- **印刷は端末依存**：iPhone は AirPrint、PCは通常の印刷。プリンターによって余白の出方が違うため、A4の内側に余裕を持ったレイアウトにする。
- **対象は数学のみ**：他教科は単元マスタとテンプレートの追加で拡張できる形にはするが、v1〜v1.2 では扱わない。

## 9.5 UIの設計原則（2026-11-15 清水さんの追加指示）

最終的には「学習者が迷わないユーザーインターフェース」にする。

- 各画面で「いま何をするところか」と「次に押すもの」が一目で分かる。主要なボタンは1画面に1つを基本とし、ステップ表示を継続する。
- 言葉は中高生に分かる平易な日本語。専門用語にはひと言の説明を添える。
- 戻る／ホームへの道筋を常に用意し、入力途中の内容は消えない（自動の下書き保存を全画面で維持）。
- 迷いやすい箇所（確定と下書きの違い、解き直しの入口など）は、画面上の案内文で補う。
- 最終フェーズの仕上げで、画面遷移全体を通して「迷わないか」の見直しを行う。
